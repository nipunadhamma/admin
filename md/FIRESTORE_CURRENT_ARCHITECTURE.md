# 13. Request Status Flow

Current status flow is:

```text
pending
   │
   ▼
guide_selected
   │
   ▼
quotation_sent
   │
   ├── quotation_accepted
   │
   ├── quotation_rejected
   │
   └── completed
```

Meaning:

```text
pending
```

Tourist created the request.

```text
guide_selected
```

Tourist selected a Guide.

```text
quotation_sent
```

Guide sent a quotation.

```text
quotation_accepted
```

Tourist accepted the quotation.

```text
quotation_rejected
```

Tourist rejected the quotation.

```text
completed
```

Trip/request process completed.

These two IDs must NOT be confused.

## Trip ID

Current architecture:

```text
Trip ID = Tourist UID
```

because:

```text
lankaQuestTouristTrips/{touristUID}
```

---

## Request ID

Current architecture:

```text
Request ID = Firestore auto-generated document ID
```

because:

```text
lankaQuestQuotationRequests/{requestId}
```

# 16. Relationship

The relationship is:

```text
Firebase UID
     │
     ├──────────────► lankaQuestTourists/{UID}
     │
     ├──────────────► lankaQuestTouristTrips/{UID}
     │
     └──────────────► lankaQuestGuides/{UID}
```

Then:

```text
lankaQuestTouristTrips/{UID}
     │
     │ tripId
     ▼
lankaQuestQuotationRequests/{requestId}
```

Then:

```text
lankaQuestQuotationRequests/{requestId}
     │
     │ guideId
     ▼
lankaQuestGuides/{guideUID}
```

Then:

```text
lankaQuestQuotationRequests/{requestId}
     │
     │ requestId
     ▼
lankaQuestQuotations/{quotationId}
```

# 18. Quotation Document ID

Current Guide quotation code creates a quotation using Firestore document creation.

Therefore the quotation document ID is:

```text
Firestore auto-generated quotation ID
```

Structure:

```text
lankaQuestQuotations
    │
    ├── {quotationId}
    ├── {quotationId}
    └── {quotationId}
```

---

# 19. Important Quotation Relationship

The quotation must contain a connection back to the request.

Primary relationship:

```text
quotation.requestId
```

Backup/legacy-compatible field currently supported by the Tourist Dashboard:

```text
quotation.requestFirestoreId
```

The main architecture should use:

```text
requestId
```

as the canonical relationship.

---

# 20. Quotation → Tourist

Quotation records are connected to the Tourist through:

```text
touristId
```

Therefore:

```text
lankaQuestQuotations/{quotationId}

    touristId
        ↓
lankaQuestTourists/{touristUID}
```

---

# 21. Quotation → Guide

Quotation records are connected to the Guide through the Guide UID.

Conceptually:

```text
guideId
        ↓
lankaQuestGuides/{guideUID}
```

The Guide is the person who creates the quotation.

# 23. ID TYPES

| ID                    | Source                   | Used For                      |
| --------------------- | ------------------------ | ----------------------------- |
| Firebase UID          | Firebase Authentication  | Tourist/Guide identity        |
| Tourist Document ID   | Firebase UID             | Tourist profile               |
| Guide Document ID     | Firebase UID             | Guide profile                 |
| Trip Document ID      | Firebase UID             | Current Tourist trip          |
| Request Document ID   | Firestore auto-ID        | Quotation request             |
| Quotation Document ID | Firestore auto-ID        | Guide quotation               |
| `tripId`              | Current Trip document ID | Links request to trip         |
| `requestId`           | Request document ID      | Links quotation/request/pages |
| `guideId`             | Guide Firebase UID       | Links request to guide        |

# 24. Attraction IDs

Tourist attraction IDs such as:

```text
sigiriya
dambulla
pidurangala
kandy
```

are NOT Firestore document IDs in the current attraction generator system.

They originate from:

```text
js/places.js
```

and are used as attraction identifiers.

Example:

```text
place.id = "sigiriya"
```

These are application/content IDs, not Firebase Authentication UIDs.

---

# 25. Authentication vs Firestore IDs

Important distinction:

```text
Firebase Authentication
        ↓
UID
```

is the identity of the user.

Firestore:

```text
lankaQuestTourists/{UID}
```

uses that UID as the profile document ID.

Firestore:

```text
lankaQuestGuides/{UID}
```

uses the same concept for Guide identity.

But:

```text
lankaQuestQuotationRequests/{requestId}
```

uses a Firestore-generated document ID.

# 28. Important Current Architecture Note

The current repository contains some older Trip Planner `localStorage` logic.

In particular, `trip-planner.js` currently still reads/writes destination and planner UI data using localStorage before the final Firestore trip save.

This means the architecture is currently **partially migrated**:

```text
Attraction selection
        ↓
localStorage
        ↓
Trip Planner UI
        ↓
Firestore
```

The intended production architecture should eventually become:

```text
Firebase Auth
        ↓
Firestore
        ↓
lankaQuestTouristTrips/{UID}
```

with localStorage used only for temporary UI/session purposes, if needed.

Business data should ultimately remain in Firestore.

# 34. Important Development Rule

Before adding a new Firestore collection, first check whether the data belongs inside one of the existing collections.

Do not create duplicate collections such as:

```text
touristTrips
trips
myTrips
requests
guideRequests
quotations
guideQuotations
```

if the same business data already belongs to:

```text
lankaQuestTouristTrips
lankaQuestQuotationRequests
lankaQuestQuotations
```

The existing naming convention should remain consistent.
